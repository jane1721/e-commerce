- 스프링부트 애플리케이션을 도커 이미지로 빌드
- mysql, redis, kafka 모두 도커 컨테이너로 이관
- 스프링부트 애플리케이션 컨테이너 실행 및 mysql, redis, kafka 연동 성공
- k6 를 활용하여 테스트 시나리오 기반 테스트 스크립트 작성 및 실행
- 결과 분석 및 개선 방안 수립..(추후 더 자세히 분석해 볼 예정)

### 실행 결과 분석
k6 를 사용하여 테스트 시나리오 에 대한 부하 테스트를 실행한 결과 지표에 대한 설명입니다.

**1. API 상태**
- GET /api/items: 59% 성공 (606번 성공, 413번 실패)
  - GET /api/items 는 상태 코드 200을 반환해야 하지만 실패한 요청이 413번
- POST /api/orders: 78% 성공 (775번 성공, 209번 실패)
  - POST /api/orders 는 상태 코드 201을 반환해야 하지만 실패한 요청이 209번
- GET /api/orders/{id}: 81% 성공 (198번 성공, 46번 실패)
  - GET /api/orders/{id}는 상태 코드 200을 반환해야 하지만 실패한 요청이 46번

**2. 전체 테스트 결과**
- 성공한 검사: 1579번 (2247번 중, 70.27%)
- 실패한 요청: 668번 (2247번 중, 29.72%)

**3. 대기 시간 및 요청 처리 시간**
- http_req_duration (요청 처리 시간): 평균 15.15초 
- 최소: 99.33ms, 최대: 51.8초 
- 90%의 요청이 43.99초 이하로 완료
- http_req_waiting (서버 응답 대기 시간): 평균 15.14초 
- 이 값은 서버가 응답을 보내기까지의 대기 시간입니다.

**4. 기타 통계** 
- 요청 실패율: 29.72%로 꽤 높은 실패율을 기록하고 있습니다. 이는 테스트 도중 일부 요청이 예상한 상태 코드 또는 응답을 반환하지 않았다는 것을 의미합니다. 
- 반환된 데이터량: 약 1.5MB의 데이터를 수신하고, 504KB의 데이터를 전송했습니다.

**5. 요청 처리 세부 정보** 
- http_req_blocked (요청 차단 시간): 평균 154.09ms로, 요청이 차단되는 데 걸린 시간입니다.
- http_req_connecting (연결 시간): 평균 89.29ms로 서버와의 연결을 설정하는 데 걸린 시간입니다.
- http_req_sending (데이터 전송 시간): 평균 4.46ms로 서버에 데이터를 전송하는 데 걸린 시간입니다.
- http_req_receiving (데이터 수신 시간): 평균 2.21ms로 서버로부터 데이터를 받는 데 걸린 시간입니다.

**6. 부하 테스트 진행 상태**
- VUs (Virtual Users): 1000명의 가상 사용자가 테스트를 수행 중입니다. 현재 635명의 사용자가 활동 중입니다.
- 테스트 지속 시간: 1분 0.3초 동안 테스트가 진행되었습니다.
- 완료된 반복 횟수: 453번, 중단된 반복 횟수: 611번

### 성능 분석 및 병목 탐색, 개선 방안
**1. 성능 분석**

- **요청 실패율**: 전체 요청 중 약 **30%**가 실패. 주요 원인은 서버 과부하 또는 네트워크 지연으로 추정
- **응답 시간**: 평균 **15초**로 길고, 일부 요청은 **51초**까지 소요
- **병목 분석**:
  - **서버 리소스 부족** (CPU, 메모리)으로 응답 지연 발생 가능
  - **네트워크 지연**: 요청 차단 시간이 평균 **154ms**로 다소 긴 편

**2. 개선 방안**

- **서버 성능 개선**:
  - **리소스 확장**: CPU 와 메모리를 증설하거나, 서버 분산 처리로 부하 분산
  - **쿼리 최적화**: 비효율적인 데이터베이스 쿼리 개선 및 트랜잭션 최적화
- **상품 조회 캐시 활용**:
  - **상품 정보 캐싱**: 빈번하게 조회되는 상품 정보는 캐시(예: Redis)를 사용하여 DB 접근을 줄이고 응답 시간을 단축

**3. 장애 대응 방안**

- **모니터링 강화**: 시스템 성능 모니터링 도구를 활용하여 장애 발생 시 즉시 대응
- **재시도 메커니즘**: 실패한 요청에 대해 재시도를 적용해 네트워크 문제 해결
